# 日次終了チェックリスト

> いつ使うか（トリガー）: **その日の作業が一区切りついたとき、毎回。** `templates/提出前チェックリスト.md`（提出直前専用）とは別物——こちらは提出の有無に関係なく、日々の運用として行う。
> 目的: 情報を足し続けると参照コストが指数的に増えます（同じ事実が何箇所にも重複し、どれが正か分からなくなる）。**肥大化・重複を溜め込まず、その日のうちに整理する。**
> 配置ルール（新しい事実をどこに書くか）は [`../_START_HERE.md`](../_START_HERE.md)「4」を参照。ここで見つけた教訓は`../LESSONS.md`に追記していってください。

---

## チェック項目

- [ ] **今日の`SESSION_LOG_YYYY-MM-DD.md`は当日分のみで、前日以前の分がルート直下に残っていないか。** 日付が変わって新しいSESSION_LOGを書き始めたら、前日分は`archive/session_logs/`へ移す（`mv`で移動するだけ。削除ではない）。移動したら、他ファイルからその日付のSESSION_LOGへの参照が`archive/session_logs/`込みのパスになっているか`grep`で確認する（見出し・パスの変更は他ファイルからの参照を壊すことがある）。
- [ ] **今日新しく作った/大きく増えたファイルで、単体3万字を超えたものは無いか。** 超えている場合、内容を分割すべきか（過剰な細分化はしないこと・`_START_HERE.md`参照）、それとも単に情報量が多いだけで妥当か（例: `input/profile/04_職務経歴.md`のような正本ファイルは大きくて構わない）を判断する。目安の確認コマンド:
  ```bash
  find . -name "*.md" -not -path "*/documents/output/pdf/*" -exec wc -c {} \; | sort -rn | head -10
  ```
- [ ] **今日追加した代表的な事実（金額・固有名詞・日付等）が、何箇所のファイルに書かれているか。** 目安の確認コマンド（事実を実際の語句に置き換えて実行）:
  ```bash
  grep -rl "確認したい語句" --include="*.md" . | wc -l
  ```
  正本1箇所＋役割の異なる層（`documents`の提出書類、`interview`の面接準備）で数箇所ヒットするのは正常。**5箇所を超えて増えている、または同じ役割の層に重複して書かれている場合は、どちらかをリンクに置き換えられないか検討する。**
- [ ] **今日生成した過程資料（模擬面接の生データ、書類のセルフレビュー草稿等）は、完了したら分離・アーカイブすべき対象か確認する。**
  - 模擬面接の質問・回答（生データ）→ `interview/companies/*/mock/raw/`
  - 模擬面接の分析結果 → `interview/companies/*/mock/analysis/`（日常参照はこちらだけで足りる）
  - 提出完了後の書類セルフレビュー・構成案・LinkedIn更新案 → `documents/output/md/_archive/`
- [ ] ⚠️ **今日、構造・フロー・仕組み（`scripts/`の挙動、md見出し構造、出力先ディレクトリ等）を変更したか。変更したなら`../ARCHITECTURE.md`は更新済みか。** 「後で更新する」は不可——古くなった`ARCHITECTURE.md`は無いより有害。今日変更していなければこの項目はスキップしてよい。
- [ ] **新しく追加した情報は、「どこか1箇所」に書くという原則を守れているか。** 迷ったら`_START_HERE.md`「4. 新しい事実をどこに書くか」の表を参照。既存箇所に書くべきものを新しい場所に複製していないか、この時点で確認する（後から気づくと修正コストが上がる——今日のうちに直す方が安い）。

## この確認自体を省略してよいとき

- セッションが短時間（数十分程度）で、ファイルの追加・大幅な編集が無かった場合は、このチェックリスト自体を省略してよい。**「毎回やること」自体が新たな固定コストにならないよう、実質的な変更があった日だけ行う。**

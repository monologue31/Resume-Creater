## 输出

**形式ごとにフォルダを分けて出力する。この構成は必ず守ること。**

```
documents/output/
├── md/     … .md ファイル（単一の情報源＝ここだけが正本）
│   ├── 履歴書{接尾辞}.md
│   ├── 職務経歴書{接尾辞}.md
│   ├── REVIEW{接尾辞}.md        ← セルフレビューも .md なのでここ（生成中の応募先分のみ）
│   └── _archive/                ← 提出完了後、役目を終えた過程資料を移す置き場（削除ではない）
│                                    REVIEW・英文レジュメ_構成案・LinkedIn更新案 等。日次終了チェックリスト参照
└── pdf/    … .pdf ファイル（提出用。md から機械生成される）
    ├── 履歴書{接尾辞}.pdf
    └── 職務経歴書{接尾辞}.pdf
```

分量の目安: 履歴書 A4 1〜2枚、職務経歴書 A4 2〜3枚。
**方針（2026-08-04）: 分量調整は `documents/output/md/` 側でのみ行い、`input/profile/04_職務経歴.md`（正本）は変更しない。** 古い・優先度の低い案件（10年以上前のメインフレーム／MES案件など）は、提出書類側では詳細記述を「在籍事実・期間・役割・使用技術」のみの沿革レベルに圧縮してよいが、`input/`側には常に完全な詳細を残す。

### PDF の作り方
`scripts/build_pdf.py` を使う。**html を経由しない**（2026-08 に廃止。以前は md/html/build_pdf.py の3箇所を手作業で同期していたが、手作業同期による内容齟齬が繰り返し発生したため、`build_pdf.py` が `documents/output/md/履歴書{接尾辞}.md` と `職務経歴書{接尾辞}.md` を直接パースして reportlab で組版する構成に変更した。**md の文言を変えるだけで pdf に反映される**——build_pdf.py 側のソースコードを内容ごとに書き換える必要はない。
実行: `python3 scripts/build_pdf.py`。Noto Sans CJK JP（Linux）またはヒラギノ角ゴシック（macOS）を CFF→TTF 変換してサブセット埋め込みする（`scripts/build_pdf.py` の `FONT_CANDIDATES` 参照。使用文字が変わればキャッシュは自動的に再生成される）。
md 側の記法との対応: 表セル内の `**太字**` は職務経歴書では黄色マーカー、履歴書では通常の太字になる。`★` は赤字強調になる。見出し構造（`## `/`### `/`#### `、`| 項目 | 内容 |` 表、`- key: value` 箇条書き）を崩すと解析できなくなるため、既存ファイルの構造パターンを踏襲すること。
組版上の注意: 和欧混在のため**両端揃えにしない**（欧文の語間が伸びる）。`wordWrap="CJK"` と `splitLongWords=0` を維持すること。

`{接尾辞}` は `apply/07_応募先.md` の指定に従う。未指定なら空文字。
**`apply/07_応募先.md` に候補が複数ある場合は、候補ごとに上記1〜5の一式を出力する**（`REVIEW.md` は候補ごとに `REVIEW_{接尾辞}.md`）。共通部分をコピーするのではなく、候補ごとに職務要約・自己PR・志望動機の重心を変えること。

**方針: 顧客の業界は事実として記載するが、業界特化を売りとしては打ち出さない。** 応募先の担当業界と自分の実務経験の業界が異なる場合、経験のある別業界の実績を「〇〇業界に強い」という打ち出し方にすると、「では応募先の担当業界の経験は？」という弱点に自ら誘導することになる。顧客業種を隠したり曖昧にしたりはしないが、能力・規模・要求水準（大規模・高信頼性環境での実績、等）で語り、業種を先頭に立てないこと（応募先の担当業界と経験業界が一致する場合はこの限りではない）。

### ⚠️ 実顧客名の扱い（2026-08-05 方針格上げ・恒久ルール）
**従来は「提出書類（`documents/`配下）では匿名化する」という方針だったが、`input/`を含むプロジェクト全体で実名を一切扱わない方針に格上げする。** 業種・規模等の匿名化ラベル（「大手金融グループ」「案件D」等）は既に一意の識別子として機能しており、実名が無くても情報は失われない。社内評価文書等、実名を含む一次資料を`input/`に取り込む場合も、**取り込みの時点で実名を除去し、既存の匿名ラベルのみで記録する**こと（マッピング表等、実名を一時的にでも記載する形も取らない）。

### ⚠️ 日本語職務経歴書のセクション順序（2026-08-05 本人指示・恒久ルール）
**職務経歴書のセクション順序は以下で固定する**（本人の明示的な指示による構成変更）:

1. 職務要約
2. 活かせる経験・知識・スキル
3. マネジメント経験・語学（1つのバンドにまとめる。語学は3行程度と短く、独立見出しにすると分量面で不利なため）
4. 自己PR
5. 職務経歴（案件詳細）
6. テクニカルスキル
7. 保有資格（詳細一覧は参照情報のため最後に配置）

**理由**: 要約・強み・PRを先に読ませ、その裏付けとしての案件詳細を後に置く構成の方が、読み手が最初の1ページで判断材料を得られるため。

⚠️ **この順序は `scripts/build_pdf.py` の `build_shokumu()` 内でハードコードされている**（`band(...)` 呼び出しの順序）。**md ファイル（`職務経歴書_{接尾辞}_ja.md`）内の物理的な見出し順序を変えるだけでは PDF の出力順序は変わらない**——各セクションは `secs["セクション名"]` という辞書参照で取得され、PDF内での出力順序はコード側の記述順が決定する。**セクション順序を変更する場合は、md とコードの両方を同時に変更すること。**

### ⚠️ 提出用PDFでのハイライト（2026-08-05 本人指示・恒久ルール）
**提出用PDFでは黄色ハイライトを使用しない。** md の `**太字**` は「ここが要点である」という意味的マークアップとして正本に残し続けるが、レンダリング側では太字（bold）として表示し、黄色背景等の視覚的強調は行わない。
- `scripts/build_pdf.py` には `_bold()`（太字のみ）と `_bold_hl()`（黄色ハイライト付き太字、`hl()`使用）の2種類の変換関数がある。**履歴書（`build_rirekisho()`）・英文レジュメ（`build_resume_en()`）はもともと `_bold()` のみを使用しており、黄色ハイライトは職務経歴書（`build_shokumu()`）のみで使われていた。** 2026-08-05、`build_shokumu()` 内の呼び出しを `_bold_hl()` → `_bold()` に変更し、3書類（履歴書・職務経歴書・英文レジュメ）の見た目の方針を「太字のみ、ハイライトなし」で統一した。
- ⚠️ **`hl()`・`_bold_hl()` 自体は削除していない。** 内部レビュー用に色付きで確認したい場面があれば、`build_shokumu()` 内の該当呼び出しを `_bold_hl()` に戻すだけで復活できる（機構自体を壊さない、という判断）。

### ⚠️ 表の狭いラベル列でのラテン文字語中改行（2026-08-05 恒久ルール・reportlab の制約）
`scripts/build_pdf.py` の `S()` は `wordWrap="CJK"` を既定にしており（日本語を文字単位で折り返すため）、同時に `splitLongWords=0`（英単語を語中で割らない）も設定している。**しかし reportlab の実装上、`wordWrap="CJK"` 使用時は `splitLongWords` が一切参照されない**（`Paragraph.breakLinesCJK()` → `wordSplit()` → `dumbSplit()` の経路は文字幅だけで機械的に折り返し位置を決めるため）。ソースコードを実際に確認して判明した既知の制約であり、設定ミスではない。
- そのため、**幅の狭い表ラベル列（`kv()` の既定 `label_w=23mm` 等）に英単語（特に `ServiceNow` のような8文字以上の語）を含む文言を置くと、語中で改行される**（実例: 「ServiceNow パートナー窓口」→「ServiceNo」＋「w パートナー」＋「窓口」に分割。2026-08-05 発覚・修正）。
- **対応方針**: 狭いラベル列に英単語を含めない（日本語のみにする、または英単語部分は値側の列に逃がす）。列幅を広げて対応する方法もあるが、`kv()` の既定幅は文書全体の多数のテーブルで共用されているため、**個別テーブルの表示のためだけに既定幅を変更しない**（ページ数・他セクションのレイアウトへの副作用を避けるため）。
- 新しいラベルを追加する際は、`python3 -c "from reportlab.pdfbase.pdfmetrics import stringWidth; print(stringWidth('ラベル文字列','JPB',9))"` 等でおおよその幅を確認し、列の実効幅（列幅 − 左右パディング計4mm）に収まるかを事前に確認するとよい。

### ⚠️ PDF生成のタイミング（2026-08-04 恒久ルール）
**既定の動作は「md のみ更新」。PDF は明示的に「PDF を生成してください」と指示されたときだけ生成する。** 「修正して」「反映して」等の指示だけでは PDF 生成を含めない（日本語版・英語版とも、すべての成果物に適用）。
`scripts/check.py` が「md が pdf より新しい」と警告する状態が常態化するが、**これは想定通り。警告を消すためだけに PDF を生成しないこと。**

### ⚠️ 構造・フローに関わる変更は、先に `ARCHITECTURE.md` を確認してから行う（2026-08-06 恒久ルール）
`scripts/build_pdf.py`・`scripts/check.py`の挙動変更、md の見出し構造・出力先ディレクトリの変更など、**「文言を直す」を超えて構造・フロー・仕組みに関わる変更**を行う前に、必ず [`../ARCHITECTURE.md`](../ARCHITECTURE.md) を読み、現状の構成・データフロー・既存の仕組み（`KeepTogether`のような見えない結合等）を確認してから、その変更が既存のデータフロー・依存関係にどう影響するかを検証する。**「変更してから影響を確認する」ではなく「影響を確認してから変更する」の順序を守ること**。
- **構造を変更したら、同じ作業の中で`ARCHITECTURE.md`も必ず更新する。** 「後で更新する」は不可——「承認された」ことと「実際に成果物に入っている」ことは別であり、同じ失敗パターンになる。
- `ARCHITECTURE.md`が実際の構造と食い違っていないかは、冒頭の「最終更新日」「この図が対応するプロジェクトの状態」を見て判断する。古い可能性がある場合は、鵜呑みにせず実際のファイル・コードを確認する（「疑ってから確認する」姿勢）。

### ⚠️ 書類冒頭の「作成日」は提出日に合わせて更新する（2026-08-05 恒久ルール）
`職務経歴書_{接尾辞}_ja.md`・`履歴書_{接尾辞}_ja.md`冒頭の「YYYY年M月D日現在」は、**md編集を始めた日ではなく、実際に提出する日付に合わせる**。この日付は`scripts/build_pdf.py`の`_extract_date()`がmdの見出し直下から動的に抽出しているだけで、コード側にハードコードされた日付は無い（過去に`build_pdf.py`側で日付がハードコードされmdと食い違っていた事例があったが、md単一情報源へのリファクタで解消済み。2026-08-05再確認済み）。
- **提出が当日でない場合、提出直前に必ずこの日付を実際の提出日へ更新してから、PDFを再生成する。** 古い日付のまま提出すると「使い回し」の印象を与えるリスクがある。
- 英文レジュメ（`Resume_{接尾辞}_en.md`）は米国式の慣行に従い、この種の「作成日」表記を**そもそも含めない**（意図的な設計であり、抜けではない）。
- この確認は`templates/提出前チェックリスト.md`にも項目として追加済み。

## 硬性规则（違反したら作り直し）

### 日本語・表記
- 全文は敬体（です・ます）。職務経歴書の案件記述のみ体言止め可。
- 年は**西暦で統一**。`input` が和暦なら西暦に、混在していれば西暦に寄せる。ドキュメント内で絶対に混在させない。
- 「御社」は話し言葉。書類は必ず**「貴社」**。
- 数字は半角、単位は「名・件・％・万円」。
- 職歴の最終行は必ず `現在に至る` → 改行 → 右寄せで `以上`。
- 学歴と職歴は見出しを分け、それぞれ中央寄せの `学歴` `職歴` 行を立てる。
- 会社名は初出で正式名称（株式会社を省略しない）。以降は略称可。
- 空欄禁止。書くことが無い欄は `特になし` / `なし`。

### 内容
- **捏造禁止。** `input` に無い経験・数字・資格を作らない。
- 数字が無い成果は、盛るのではなく「何をどう改善したか」を具体的な動詞で書く。数字が欲しい箇所は `REVIEW.md` に質問として立てる。
- 転職理由は事実を歪めずポジティブ変換する（例：残業が多い → 「業務効率化に主体的に取り組める環境で成長したい」）。前職の批判は一切書かない。
- 職務経歴書の各案件は **課題 → 施策 → 成果** の順。1 案件 150〜250 字。
- 冒頭に **職務要約**（3〜4 行、キャリアの全体像＋一番強い実績）を置く。人事はここしか読まないことがある。
- 自己PR は 300〜400 字、強み 1 つに絞りエピソードで裏付ける。強みの羅列はしない。

### 岗位定制（`apply/07_応募先.md` に JD がある場合のみ）
- JD の要求スキルを抽出し、**合致する経験を職務要約と自己PRの前方に配置**し直す。
- 関連の薄い案件は削除せず**圧縮**（1〜2 行）。時系列の欠落を作らない。
- JD のキーワードを、事実を曲げない範囲で本文の語彙に採用する（ATS 対策）。
- 志望動機は JD と `06_志望動機_希望条件_{接尾辞}.md`（＋`input/apply/志望動機/00_不変の軸.md`・`志望動機/ロール_{職種}.md`）のタネから作文。応募先固有の事業・製品に触れる。汎用文にしない。
- JD が空の場合は汎用版を作り、志望動機欄は `※応募先ごとに追記` と明記する。

## セルフレビュー（`documents/output/md/REVIEW.md`）

生成後、自分の出力を人事担当の目で読み直し、以下を書く。褒めなくていい。

1. **要確認事項** — 事実確認が必要な箇所、input に無くて推測で埋めた箇所（あれば全部）
2. **数字が欲しい箇所** — 具体的にどの案件のどこに、どんな指標があると強くなるか
3. **職歴の空白期間** — 1 ヶ月以上のブランクがあれば指摘し、面接での説明案を添える
4. **突っ込まれそうな点** — 面接官が聞いてくる質問 3 つと、回答の方向性
5. **JD 適合度**（定制時のみ）— 満たしている要件 / 満たしていない要件 / それをどう補うか

## 実行手順

1. `input/` を全ファイル読む。`apply/07_応募先.md` の JD 有無で定制モードを判定。
2. 情報を時系列・カテゴリに正規化（年月の表記ゆれ、社名ゆれを統一）。
3. `documents/output/md/*.md` を先に書く。内容の勝負はここで終わらせる。
4. `python3 scripts/build_pdf.py` を実行し、md から pdf を生成する。
5. `REVIEW.md` を書く。
6. 生成ファイルを present_files でユーザーに提示し、**要確認事項のうち重要な 2〜3 点だけ**を口頭で伝える。REVIEW.md の全文を会話に貼らない。

## 再実行について

- `input/` を書き換えて再実行 → `documents/output/` を上書き。
- `apply/07_応募先.md` だけ差し替えて再実行 → 接尾辞違いの別ファイルが増える（既存の他社版は消さない）。
- ユーザーが「3 番目の案件をもっと短く」等と部分修正を求めたら、**全体を再生成せず該当箇所だけ編集**し、`python3 scripts/build_pdf.py` を再実行して pdf に反映させる（md が唯一の情報源のため、同期作業は不要）。

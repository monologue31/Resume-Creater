# 提出前チェックリスト

> いつ使うか（トリガー）: **応募書類一式（レジュメ・職務経歴書・推薦文等）を提出する直前**。`scripts/check.py` の自動チェックとは**別物**であり、**スクリプトでは拾えない、人間の判断が必要な項目**だけをここに絞っている。
> 判断原則: [`../LESSONS.md`](../LESSONS.md) — 各項目の理由付けはそちらを参照。
> 自動チェック: `python3 scripts/check.py`（★の残存・PDF/mdの日付整合・KEY_FACTSの数値整合を機械的に検出する。**まずこれを実行してから**、以下の人的チェックに進むこと）

---

## チェック項目

- [ ] ⚠️ **承認された変更が、実際に成果物へ反映されているか——網羅的な突き合わせ監査（最重要・教訓22）**。「承認された」「実施したと報告した」ことと「成果物に実際に入っている」ことは別である（3件の実例あり: 2026-08-04兼務訂正・2026-08-05トレンドマイクロ2製品目・2026-08-05自己PR MID Server追記、いずれも承認済みなのに未反映のまま見過ごされていた）。**手順**: `SESSION_LOG_*.md`に記録された決定事項を1件ずつリストアップし、`grep`等で提出書類（`documents/output/{接尾辞}/md/`配下）に実在するかを機械的に確認する。「①反映済み／②未反映（要修正）／③意図的に未反映」の3分類で結果を残す。**スポットチェックでは不十分——網羅的に行うこと。**
- [ ] ⚠️ **職務経歴書・履歴書（JIS形式）冒頭の「作成日」が、実際の提出日と一致しているか**（`documents/PROMPT.md`「書類冒頭の作成日」ルール参照）。**古い日付のまま提出すると「使い回し」の印象を与える。** 提出日が変わった場合は必ずmdを更新してからPDFを再生成する。英文レジュメには元々この日付表記が無いことも確認する
- [ ] **★（未確認事項）が提出書類に残っていないか**（`check.py`で機械検出されるが、生成直後は必ず目視でも確認する。教訓7）
- [ ] **顧客名・プロジェクトコードネームが匿名化されているか**。既存の匿名化方針（「大手金融グループ」等の表記）と新しく追加した記述が矛盾していないか
- [ ] **業界特化・特定領域の強調に偏っていないか**。応募先の担当領域と無関係な強みを前面に出し、弱点（未経験領域）に自ら注意を向けていないか確認する（教訓12）
- [ ] **数値にスコープが明示されているか**。金額・人数等が「誰の・何に対する数字か」を明示せず単独で書かれていないか（教訓6）
- [ ] **事実と解釈が混在していないか**。提出書類（レジュメ・職務経歴書）に、検証不能な意味づけ・自己評価・他製品との類推が紛れ込んでいないか（教訓8）
- [ ] **書類事実性監査を完了したか**。新規・変更した主張について、[`書類事実性監査.md`](書類事実性監査.md)を使い`input/`正本への根拠、案件をまたぐ誤接続、資格の取得状態、強い動詞を確認し、結果を`documents/output/{接尾辞}/md/事実性監査_{接尾辞}.md`に残す
- [ ] **PDFのATS文字層とJDキーワードを検証したか**。[`ATS・JDキーワード検証.md`](ATS・JDキーワード検証.md)を使い、氏名・連絡先・見出しが抽出できること、文字化けがないこと、主要JD語が根拠に基づいて載っていることを確認する。未経験の語は詰め込まずギャップとして記録する
- [ ] **文書間で事実が矛盾していないか**（レジュメ・職務経歴書・推薦文・LinkedIn等の間で、期間・金額・役割の記述が一致しているか）
- [ ] **推薦文がある場合、紹介者との関係の実態と文面が整合しているか**（詳細は`推薦文ジェネレータ/チェックリスト.md`を使う。ここでは全体整合のみ確認）
- [ ] **公開プロフィール（LinkedIn等）を更新した場合、現職に転職活動が露見する見た目になっていないか**（教訓13）
- [ ] **本人の最終承認を得たか**（提出・送付前の最後のゲート）
